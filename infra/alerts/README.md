# Alerts

Lane B094. Alert rules for B093's SLOs and for failure signals, their routing to people, and the
checks that keep both honest. What a severity asks of on-call, the rotation and incident roles are
in the [on-call handbook](../../docs/ops/oncall.md); each alert's runbook is
`infra/runbooks/alerts/<alert>.md`.

Alerting release: v1

## Layout

| Path                                                        | Holds                                                                                              |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `rules/<service>.rules.yaml`                                | One file per service: every threshold for that service (Prometheus rule format, for Mimir's ruler) |
| `rules/<service>.nonprod.rules.yaml`                        | Rules for dev and stage only, the one place `pending_metric` is allowed                            |
| `rules/<service>.test.yaml`                                 | `promtool test rules` unit tests for that file                                                     |
| `recording/slo-30m.rules.yaml`                              | The 30m SLO windows, generated by `slo-windows.mjs` (B093 records 5m, 1h, 6h and 3d)               |
| `alertmanager/alertmanager.yml`                             | Routing: receivers without integrations, timings, inhibition                                       |
| `alertmanager/centcom.tmpl`                                 | Notification text                                                                                  |
| `exporters.yaml`                                            | Exporter metrics the rules may read, beside B093's catalogue                                       |
| `lint.mjs`, `promtool.mjs`, `render.mjs`, `slo-windows.mjs` | The commands below                                                                                 |

Deploy the rules with Mimir's ruler: `mimirtool rules load infra/observability/slo/rules.yaml
infra/alerts/recording/*.yaml infra/alerts/rules/*.rules.yaml` for dev and stage, and without the
`*.nonprod.rules.yaml` files for prod.

## The alerts

| Alert                     | Severity     | Service   | Owner        | Fires when                                                                                                              |
| ------------------------- | ------------ | --------- | ------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `ApiAvailabilityFastBurn` | page         | api       | platform     | `api-availability` burns 14.4x over 1 h and 5 m                                                                         |
| `ApiAvailabilitySlowBurn` | page, ticket | api       | platform     | 6x over 6 h and 30 m (page); 3x over 3 d and 6 h (ticket)                                                               |
| `ApiLatencyBurn`          | page, ticket | api       | platform     | `api-latency`: fast or slow burn (page); 3x over 3 d (ticket)                                                           |
| `StripeWebhookLag`        | page, ticket | api       | billing      | `stripe-webhook` fast or slow burn, or `stripe.event.process` oldest > 10 m or depth > 100 (page); 3x over 3 d (ticket) |
| `RelayConnectBurn`        | page, ticket | relay     | realtime     | `relay-connect`: fast or slow burn (page); 3x over 3 d (ticket)                                                         |
| `RelayFanoutBurn`         | page, ticket | relay     | realtime     | `relay-fanout`: fast or slow burn (page); 3x over 3 d (ticket)                                                          |
| `ResumeFailureBurn`       | page, ticket | relay     | realtime     | `resume-success`: fast or slow burn (page); 3x over 3 d (ticket)                                                        |

| `RelayConnectionDrop`     | ticket       | relay     | realtime     | a region's connections fall over 30 % in 5 m (from at least 100)                                                        |

| `DbPoolSaturation`        | ticket       | postgres  | platform     | a service's pool over 90 % in use for 5 m                                                                               |
| `RedisMemoryHigh`         | ticket       | redis     | platform     | over 80 % of `maxmemory` for 10 m                                                                                       |
| `CertExpirySoon`          | ticket       | platform  | platform     | a served certificate expires in under 14 d                                                                              |
| `ReadyzFailing`           | ticket       | platform  | platform     | more than one instance of a component fails `/readyz` for 5 m                                                           |
| `ObservabilityDown`       | page         | platform  | platform     | a service that exported metrics an hour ago has exported nothing for 10 m                                               |

Ten alerts page, the most allowed. Every page has an SLO or a `user_impact` statement: the SLO
burns, `DeadLetterNonEmpty` (dead letters are lost after 7 days) and `ObservabilityDown` (alerting
is blind). Cause alerts that customers only notice through an SLO open tickets; the SLO pages.

### Rules for a rule

`pnpm alerts:lint` checks all of these:

- Labels: `severity` (`page`, `ticket` or `info`), `service` (the file's), `owner` (a team),
  `runbook` (`infra/runbooks/alerts/<alert>.md`), and `slo` for an SLO alert. Nothing else, and
  never a label that could hold an id.
- Annotations: `summary`, `impact` and `dashboard` (`/d/<uid>?var-env={{ $labels.env }}`, a B093
  dashboard; notifications prefix the Grafana URL), `user_impact` for a page without an SLO, and
  `pending_metric` (below). Templates may show only `$labels.env`, `region`, `queue`, `component`
  and `job`: never an id, an e-mail address or content.
- Every metric an `expr` reads is in B093's catalogue (`packages/core/src/otel/catalogue.ts`),
  recorded by a rule file, or listed in `exporters.yaml`. `pending_metric: B###` allows a lane's
  future metric, in a `.nonprod.rules.yaml` file only.
- One rule per alert and severity: combine conditions with `or` (under `max by (env)` when their
  labels differ).
- Burn rates are compared after `round(…, 0.001)`: an error rate of exactly 1.44 % against 99.9 %
  computes to 14.39999…, and the card wants it to fire.
- An alert's runbook follows `infra/runbooks/alerts/_template.md`: every section, a command or
  dashboard link in each triage step and in Verification. Runbook links must resolve.

## Routing

`alertmanager/alertmanager.yml`, grouped by `env` and `service` so an outage stays a few pages:

| Severity            | Receivers and timing                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `page`              | `pager-primary` after 30 s; `fallback` after 5 min and `pager-secondary` after 15 min unless acknowledged (silenced) first; repeats every 4 h |
| `ticket`            | `ticket`, repeated every 24 h                                                                                                                 |
| `info`              | `info`, repeated every 24 h                                                                                                                   |
| `ObservabilityDown` | also `fallback` after 30 s: the normal path may share the failure                                                                             |
| deploy marker       | `blackhole`: B092's `deploy_in_progress="true"` alert only inhibits                                                                           |

Inhibition: the deploy marker holds back `RelayConnectionDrop` in its environment, and a page holds
back the tickets and info alerts of the same service and environment.

## Contact points

Receivers get their integrations at deploy time: `pnpm alerts:render <dir>` reads one variable per
receiver and writes `<dir>/alertmanager.yml` and `<dir>/centcom.tmpl` (outside the repository: they
hold secrets). Load them with `mimirtool alertmanager load <dir>/alertmanager.yml <dir>/centcom.tmpl`.

| Variable                        | Receiver                                                                  |
| ------------------------------- | ------------------------------------------------------------------------- |
| `ALERT_CONTACT_PAGER_PRIMARY`   | `pager-primary`                                                           |
| `ALERT_CONTACT_PAGER_SECONDARY` | `pager-secondary`                                                         |
| `ALERT_CONTACT_FALLBACK`        | `fallback`                                                                |
| `ALERT_CONTACT_TICKET`          | `ticket`                                                                  |
| `ALERT_CONTACT_INFO`            | `info`                                                                    |
| `ALERT_GRAFANA_URL`             | links to dashboards in notifications                                      |
| `ALERT_RUNBOOK_BASE_URL`        | links to runbooks (ends with `/`, e.g. the repository's blob URL on main) |

Each contact point is `<kind>:<target>`:

| Kind        | Target                       | Notes                                                                                                                                  |
| ----------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `pagerduty` | an Events API v2 routing key | `page` is `critical`, others `warning`                                                                                                 |
| `opsgenie`  | an API key                   | `page` is `P1`, others `P3`                                                                                                            |
| `slack`     | an incoming webhook URL      | https only                                                                                                                             |
| `webhook`   | any http(s) URL              | Alertmanager's webhook payload (tests use a stub receiver)                                                                             |
| `email`     | an address                   | needs `ALERT_SMTP_SMARTHOST` (`host:port`) and `ALERT_SMTP_FROM`; `ALERT_SMTP_USERNAME` and `ALERT_SMTP_PASSWORD` together, or neither |
| `none`      | nothing                      | the receiver notifies nobody (dev)                                                                                                     |

Values come from the secret manager (B091); nothing in the repository holds one. A missing or
malformed variable fails the render, naming the variable but never its value.

## Commands

| Command                                       | Does                                                                                                                                          |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm alerts:lint`                            | The checks above; exits 1 listing every problem                                                                                               |
| `pnpm alerts:test`                            | `promtool check rules` and `promtool test rules` over every rule and test file, with a local `promtool` or Docker (`prom/prometheus:v2.54.1`) |
| `pnpm alerts:render <dir>`                    | The deployable Alertmanager config, from the environment                                                                                      |
| `node infra/alerts/slo-windows.mjs [--check]` | Regenerates (or checks) the 30m SLO windows after an SLO file changes                                                                         |

`pnpm test` runs the same checks (`infra/alerts/test/`): the lint and its broken fixtures, the
policy (page count, annotations, runbooks, the drill record), the renderer, and, where a container
runtime is reachable (CI's test job), `promtool`, `amtool` and a running Alertmanager with a stub
receiver for the routing, escalation, repeat and inhibition behaviour.

## Failure modes

- **The metrics pipeline is down:** `ObservabilityDown` pages, and goes to the fallback channel at
  once. If the alerting stack itself is down nothing fires; a dead man's switch on the provider's
  side is the next step (see the on-call handbook's handover checks).
- **An alert storm in a regional outage:** grouping by `env` and `service` makes one page per
  service (api, relay, worker), and pages hold back their services' tickets.
- **The paging provider is unreachable:** an unacknowledged page reaches the `fallback` contact
  point after 5 minutes, which should be another provider (Slack or e-mail).
