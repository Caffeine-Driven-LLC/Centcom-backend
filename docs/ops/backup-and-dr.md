# Backup, restore and disaster recovery (one server)

Lane B099, the part that works on the single-server layout of [deployment.md](deployment.md) with
any S3-compatible bucket (Cloudflare R2, Backblaze B2, AWS S3, MinIO). Scripts in
[`infra/dr/`](../../infra/dr/), runbooks in [`infra/runbooks/dr/`](../../infra/runbooks/dr/).

## What it does

| Script             | Does                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `backup.sh`        | One consistent snapshot of Postgres, `pg_dump`, encrypted with gpg (AES-256), uploaded with a manifest                                |
| `restore.sh`       | Downloads, checks the SHA-256 against the manifest, decrypts through a pipe into `pg_restore`, verifies                               |
| `verify.sh`        | Migration version, same tables, row count and md5 of every table, valid constraints                                                   |
| `drill.sh`         | Backup (or the latest one), restore into an isolated instance, schema diff, wrong-key and altered-file checks, `dr-drill-report.json` |
| `backup-status.sh` | Age of the newest backup; exits 1 when stale; writes `centcom_backup_age_seconds` for node_exporter                                   |
| `prune.sh`         | Deletes backups older than `BACKUP_RETENTION_DAYS` (default and maximum 35), keeps the newest three                                   |

Also `pnpm dr:backup`, `dr:restore`, `dr:verify`, `dr:drill`, `dr:status`.

- **Encryption.** Every dump is encrypted before it leaves the server: pg_dump streams into gpg,
  plaintext never touches the disk. The passphrase (`BACKUP_PASSPHRASE`) is **not** stored in the
  bucket or the repository, and is passed to gpg on a file descriptor, never a command line. An
  altered file or a wrong passphrase stops the restore before any database is touched (exit 1 / 3).
  Uploads are signed with the payload hash, so the store rejects a corrupted transfer; transport is
  TLS to R2/B2.
- **Consistency.** The dump and the manifest come from one repeatable-read snapshot, so the row
  counts and md5s in the manifest are exactly what the dump contains.
- **Isolation.** Rehearsals restore into a throwaway Postgres with `--network none`: nothing can
  reach production from it, and it is removed afterwards. Plaintext appears only inside that
  container.

## Set it up

1. **Bucket.** Cloudflare R2: create a bucket (for example `centcom-backups`), an API token with
   "Object Read & Write" on that bucket only, note the account's S3 endpoint
   `https://<account>.r2.cloudflarestorage.com`; `BACKUP_S3_REGION=auto`. Backblaze B2: create a
   private bucket and an application key limited to it; endpoint `https://s3.<region>.backblazeb2.com`,
   `BACKUP_S3_REGION=<region>`. Turn on versioning (R2 object lifecycle rules / B2 keeps versions by
   default) so a deleted or overwritten backup can be recovered.
2. **Settings.** Fill the `BACKUP_*` block of `infra/deploy/production.env`. `BACKUP_PASSPHRASE` was
   generated by `gen-env.mjs`: **copy it to the password manager and to an offline copy held by two
   named people now.** Without it the backups are noise.
3. **Schedule.** `crontab -e` and add the lines of `infra/dr/crontab.example`: nightly backup and
   prune, a freshness gauge every 15 minutes, a restore drill on the first of the month.
4. **First run.** `pnpm dr:backup && pnpm dr:drill --use-latest`: the drill must say `verified true`.

## Targets and what this layout can promise

| Target    | Figure                                                     | Why                                                                  |
| --------- | ---------------------------------------------------------- | -------------------------------------------------------------------- |
| RPO       | the backup interval, up to ~26 h (`DR_RPO_TARGET_S=93600`) | nightly dumps; point-in-time recovery needs WAL archiving, not built |
| RTO       | 60 min (`DR_RTO_TARGET_S=3600`)                            | measured by the drill; seconds to minutes at today's data size       |
| Retention | 35 days at most                                            | bounds how long a deleted account can live on in a backup            |

Measured on a development machine with the real schema (76 tables, a few hundred rows): backup 1 s,
restore plus verification 8 to 12 s, in-place restore of the live stack 26 s including the
services coming back healthy. These numbers say nothing about a database with real data in it; run
the drill against your real one and read `rto_seconds`.

`dr-drill-report.json`: `{started_at, restore_point, backup, rpo_seconds, rto_seconds,
rto_target_seconds, rpo_target_seconds, verified, checks: [{name, ok}]}`. `drill.sh` exits 5 when
the restore is over its RTO or RPO target, 4 when verification fails.

## What is not covered (read this)

- **Point-in-time recovery** is an option, off by default (`PG_ARCHIVE_MODE=off`): see "Point-in-time recovery" below. Without it, up to a day of writes can be lost.
- **Account deletions after a restore.** A restore brings back accounts deleted since the backup. The deletion log
  below records both workspaces and accounts (the account purge, B026, writes a tombstone first), and
  `pnpm tombstones:apply` deletes them again; it needs the object store the tombstones were written to. An account
  that was purged while no object store was configured has no tombstone (`account_tombstones_skipped_total`).
  `restore.sh --into stack` still refuses without `--i-know-deletions-may-reappear`, so run the apply step before
  letting anyone in.
- **Session history in the bundled MinIO.** The `minio-data` volume is on the server's disk and is
  not part of these backups. Put `OBJECT_STORE_*` on R2/B2 (versioned) to make the history durable.
- **Redis** is treated as rebuildable (rate limits, idempotency, queues): AOF is on, nothing else.
- **Second-provider replication, Terraform for the buckets, the `backup-verify` worker job** and the
  Prometheus alert rules (`BackupStale` at 26 h): not built. `backup-status.sh --prom` writes the
  gauge; the alert rule belongs to B094.
- **Scanning backups for provider credentials** (B101's `backupScanHook`) is not wired in: it is a
  separate lane (#127); call it on the plaintext stream between pg_dump and gpg when both are merged.
- The drill runs on the same machine as production. It proves the backups restore, not that the
  provider survives a region loss.

## Credential scan of dumps and restores (B101)

`backup.sh` pipes the dump through the credential scanner (`apps/api/src/scan-stream.js` in the API image, run with no
network) before it is encrypted. If a provider credential (an Anthropic or OpenAI key, an AWS or Google key, a bearer
line) is in the data, or the stream cannot be read to the end, **nothing is uploaded**: the script exits 6, keeps an
encrypted copy in `infra/deploy/.state/quarantine/`, writes a line to the history, and the owners decide. `restore.sh`
scans the decrypted stream on its way into `pg_restore` and exits 6 the same way, so a restore is not put into service
unnoticed. Settings: `BACKUP_SCAN_IMAGE` (default `centcom-api:<current tag>`), `BACKUP_SCAN_SCRIPT` (a local copy run
with the host's Node, for development), and `BACKUP_SCAN=skip` to go without, knowingly: the log warns and the manifest
records `"credential_scan":"skipped"`. A backup is refused when no scanner is available and `skip` was not given.

The dump is written uncompressed (`pg_dump --compress=0`) so the scanner can read it; the custom format compresses table data
by default, and a credential inside compressed data is invisible. Backups made before this change are compressed: a
restore scans them but cannot find a credential inside the compressed parts.

## Point-in-time recovery (option)

Cuts the data lost in a disaster from up to 26 hours (the nightly dump) to about two minutes.

1. Set `PG_ARCHIVE_MODE=on` in `production.env` and redeploy: Postgres writes every finished WAL segment, and at least
   one a minute (`archive_timeout=60`), into the `wal-archive` volume (a one-shot `wal-init` makes the volume writable).
   **Do not turn it on before step 2 runs**: nothing empties the volume but the shipper.
2. Cron (see `infra/dr/crontab.example`): `infra/dr/wal-ship.sh` every minute and `infra/dr/basebackup.sh` daily. The shipper
   encrypts each segment with the backup passphrase, uploads it to `wal/<segment>.gpg`, downloads it again and compares, and
   only then deletes it from the volume; a segment it could not ship stays and the script exits 1. The base backup
   (`pg_basebackup`, tar, gzip, encrypted) goes to `base/<stamp>.tar.gz.gpg` with a manifest.
3. Restore: `infra/dr/pitr-restore.sh --to '2026-10-14 09:58:00+00' --keep` (or `--to latest`). It picks the newest base
   backup that started before the moment, unpacks it and every shipped segment into a throwaway container with no
   network, lets Postgres replay to the moment, promotes, and prints the container name. The time must be later than the
   end of that base backup and no later than the last shipped segment.

Verified (`infra/dr/pitr.test.ts`, real Postgres and MinIO in Docker): rows written before the chosen moment are in
the restored database and rows written after it are not; `--to latest` has everything shipped; a wrong passphrase stops
before anything starts (exit 3); an unreachable bucket leaves the segments in the volume and the shipper exits 1; the
bucket holds ciphertext only. **Not verified:** a server-side disaster (the last unshipped minute is lost by design), a
real Cloudflare R2 or Backblaze B2 bucket, and archive volume sizing under real write load.

## Deletion tombstones (workspaces and accounts)

When a workspace is purged, the first purge hook writes `tombstones/workspace/<id>.json` (an id and a time) to the object
store, outside the database. When an account is purged, `purgeUser` writes `tombstones/account/<usr_id>.json` first (same
shape, still only an id and a time) and stops, to be retried by the job, if the write fails. After restoring an older backup run
`pnpm tombstones:apply --dry-run`, then `pnpm tombstones:apply`: every tombstoned workspace that the restored database holds is
marked deleted and purged again with the normal hooks, and every tombstoned account the database holds undeleted is set to
`pending_deletion` with its deadline in the past and put through the account purge (personal rows removed, audit rows
pseudonymised to `usr_deleted`, sole workspaces deleted). Accounts whose sole workspaces are still being purged, or that now block
because they own a shared workspace, are listed as "not finished"; they stay `pending_deletion`, so the worker's hourly
`account-purge` sweep finishes them (or a human decides, for a block). Idempotent; an id that is not there, or already `deleted`, is
skipped. Needs `OBJECT_STORE_*` (the same settings as the worker). Without an object store there is no log: the purge still runs
and `account_tombstones_skipped_total` counts it, so alert on it in production.
