## Goal
A person with a Raspberry Pi 4 (4 GB, 64-bit OS, Docker installed) runs one command and gets a small Centcom server on their network: sign-in, hosted sessions in command post and branch mode, invites, watch links, board notes, queue approvals and the Team section all work against it, so the whole product can be tried by two computers before any real server exists.

## In scope
- `infra/pi/`: an `docker-compose.pi.yml` (or one image, whichever is lighter; say which and why in the doc) running Postgres, Redis, the API, the relay and the worker, plus Mailpit so sign-in codes can be read in a browser; memory limits and Postgres settings tuned so the stack stays under 3 GB at idle and works on a 4 GB board; images for linux/arm64.
- `infra/pi/up.sh`, `down.sh`, `logs.sh` and `reset.sh` (bash: the Pi has no `sub`): `up.sh` generates the secrets (as `gen-env.mjs` does, nothing committed), sets `SELF_HOST_PLAN` so the Free plan can create hosted sessions, builds or pulls the arm64 images, waits for health, and prints the server's addresses and the exact settings the Centcom terminal app, the desktop app and the web app need to point at it.
- How to reach it: the local network (the default), Tailscale, and a Cloudflare Tunnel as an optional compose profile; no router port-forwarding. Where a client refuses plain `http`/`ws` for an address that is not localhost, an optional Caddy profile with its own internal certificate authority.
- `docs/ops/pi-test-server.md`: what to buy and how to set it up (USB SSD, not the SD card; cooling), the commands from a fresh Pi, how to read the sign-in code, how to test session sharing with two computers (including a branch-mode session and a watch link), how to reset, how many test users to expect it to carry, and what is not safe for production (development secrets, the in-memory mailer, no backups, no TLS by default).
- A test that the compose file parses, the generated environment has no repeated or empty secret, and no secret or key-looking value is committed (gitleaks-clean).

## Out of scope
- Production deployment (B091, B092) and backups (B099).
- Anything that needs a real mail, Stripe or Cloudflare account.
- Performance numbers from the Pi (B095 measured a laptop; the Pi proves function, not capacity).

## Build against (no counterpart needed)
The production images from B091 built for linux/arm64 (on the Pi, or with buildx and an emulator); on a development machine the compose file is exercised on x86 with different ports and throwaway volumes.

## Deliverables
- `infra/pi/`
- `docs/ops/pi-test-server.md`

## Interfaces (the only surface other lanes may use)
- `infra/pi/up.sh` prints the API address, the relay address, the mail UI address and the client settings (the environment variables or flags of the apps that choose their server).

## Acceptance criteria
1. On a Raspberry Pi 4 with 4 GB running a 64-bit OS, `infra/pi/up.sh` ends with every service healthy and the stack using under 3 GB at idle.
2. From a second computer on the same network, a person signs in with a code read from the mail UI, starts a hosted session, a second person joins by invite, and a visitor reads it through a watch link.
3. A branch-mode session between two computers shows both agents in the Team section, and a board note from one reaches the other.
4. `reset.sh` returns the server to a clean state without touching other containers on the Pi; `down.sh` stops only what `up.sh` started.
5. No secret is committed; running `up.sh` twice keeps the same secrets, and `reset.sh --new-secrets` makes new ones.

## Tests required
- pi.compose.test.ts (the file parses, limits are set, every service has a health check).
- pi.env.test.ts (generated secrets are present, distinct and not committed).
- A written manual checklist in the doc for the on-board steps, marked as not run in CI.

## Guardrails (MUST / MUST NOT)
- MUST NOT publish a port to the internet or ask the person to open one on their router.
- MUST NOT reuse the production environment template's values; generated per install.
- MUST say in the doc and in the `up.sh` output that this server is for testing only.

## Failure modes
- Not enough memory -> the script says so before starting and names what to close or which limit to lower.
- The images do not exist for the board's architecture -> `up.sh` stops with the exact architecture it found and the build command to run.
## Notes
